# ReAgent 前端体验与 Agent 执行透明化改进规划

> 编写日期：2026-09-10  
> 状态：待执行。本文仅规划改进，不代表相关功能已实现。  
> 调研范围：当前仓库的静态前端、Web API、Agent Runtime、计划执行、编排、Trace 与会话存储。结论来自源码检查，尚未进行浏览器实测或用户访谈。

## 1. 改进目标与范围

将当前以聊天和技术列表为主的页面，改造成兼顾任务交互与执行观察的 Agent 工作台。用户在任务运行中、失败后、重新打开历史会话时，都应能回答：

1. 当前任务是什么，使用哪种执行模式，现在执行到哪里？
2. 已生成哪些计划，哪些步骤完成、失败或被跳过，计划为什么发生调整？
3. 哪个 Agent 正在工作，调用了什么工具，输入、输出和耗时分别是什么？
4. 哪些记忆、技能、上下文和依赖结果参与了本次执行？
5. 出错发生在哪个环节，是否正在重试，最终结果是否包含部分失败？
6. 刷新、断线或停止之后，已发生的过程是否仍可查询？

“全透明”指可观测的执行事实、显式计划、对外决策摘要和结果依据；不要求获取模型内部隐含思维链，也不允许前端编造推理过程、进度或未采集的指标。未采集、已省略、已脱敏的数据须明确标识。

本轮规划覆盖界面设计、前端状态管理、事件协议、必要后端改造、持久化与验收。首个版本聚焦现有 `/api/web/*` 直连执行链路；Redis/Worker 链路的统一接入列入后续阶段。

## 2. 现状与问题依据

### 2.1 已有能力，应继续复用

- `app/static/index.html`、`style.css`、`app.js` 提供原生 HTML/CSS/JavaScript 页面，无独立前端构建工程。
- 已有 ReAct/Plan 切换、会话历史、文件上传、工具/技能/MCP 列表和子 Agent 档案管理。
- `/api/web/chat/stream` 已通过 SSE 推送 `step`、`tool_result`、`final`、`done`、`error`。
- 前端已有工具卡片、计划列表、带耗时的 Trace 树和编排详情，具备可复用的展示基础。
- Trace 已有父子 Span、输入输出、耗时、错误和部分上下文/模型指标；编排结果已有 SQLite 持久化与查询接口。

### 2.2 优先解决的缺口

| 维度 | 源码依据 | 问题及用户影响 | 优先级 |
| --- | --- | --- | --- |
| 信息架构 | `index.html` 将模式、工具、档案、技能、MCP、会话、文件、编排放在同一侧栏 | 管理信息挤占任务导航，缺少独立的执行观察区 | P0 |
| 视觉与适配 | `style.css` 固定 280px 侧栏，大量 10–12px 标签；未见响应式媒体查询 | 层级弱、内容密、小屏空间不足，需建立统一视觉规则 | P0 |
| 实时过程不完整 | `web.py:web_chat_stream` 在 `done` 才发送完整计划与 Trace；`app.js:send` 结束后才插入工作流面板 | 执行过程中主要看到工具卡片，计划与调用树属于事后展示 | P0 |
| 状态失真 | `handleFrame` 为等待执行的工具传入 `success: true`；`addToolMsg` 据此显示成功 | 尚未执行就出现成功图标 | P0 |
| 调用对应关系不可靠 | SSE 未传 `tc.id`；`updateToolCard` 按工具名逆序查找，未强制限定待完成状态 | 同名重复调用可能覆盖另一张卡片，并发接入后风险更高 | P0 |
| 错误与输出遗漏 | `tool_result` 将输出转字符串并截断至 300 字符，使用真假值判断；卡片更新依赖 `data.data` 为真 | `0`、`false`、空字符串及只有错误的响应可能显示不完整 | P0 |
| 历史无法完整还原 | `renderHistory` 跳过部分决策消息，工具统一按成功展示且参数为空；普通会话消息模型无运行关联字段 | 刷新后丢失计划、真实工具状态与运行关联；编排历史虽存在，但不能替代完整回合记录 | P0 |
| Plan 生命周期缺失 | `plan_loop.py` 修改步骤状态；`runtime.py:_run_plan_mode` 在内部反思和重规划，未发送对应 Web 事件 | 无法实时展示计划版本、步骤进度、失败和调整过程 | P1 |
| 子 Agent 实时断层 | `orchestrator/executor.py` 调用子 ReAct 循环时未接入 Web 的 `LoopHooks` | 主页面常只能看到 `delegate` 等待及最终结果，无法观察子任务内部进展 | P1 |
| Trace 生命周期不完整 | `TraceRecorder` 在 `end_span` 写 JSONL，`SpanStatus` 只有 `OK/ERROR` | 直接查询现有 Trace 无法完整表达正在运行、取消、等待等状态 | P1 |
| 连接与取消语义不足 | `init` 最后无条件设置已连接；停止使用 `AbortController`，服务端断流后取消任务 | 连接状态可能误报；没有可查询的取消确认和稳定终态 | P0 |
| 并发隔离风险 | Web 路由修改共享 `settings.agent_mode`；Runtime 实例保存 `_state`、`_extra_hooks` 等可变运行字段 | 并发请求存在模式、状态和事件串扰风险，实施时须复现并消除 | P0 |
| 内容渲染边界 | 多处将 `marked.parse` 输出直接写入 `innerHTML` | 在扩大工具输出、文档预览范围前，须统一 Markdown 清理和链接协议限制 | P0 |

现有 `tests/test_web.py` 覆盖静态页面、能力接口、聊天和 SSE 基础事件，但尚不能证明浏览器布局、断线续接、历史一致性及同名工具对应关系正确。

## 3. 目标界面与交互设计

### 3.1 信息架构

桌面采用“会话导航 + 任务主区 + 执行检查区”，检查区支持收起和调宽：

```text
┌──────────────┬─────────────────────────┬─────────────────────────┐
│ ReAgent      │ 当前任务 / 模式 / 状态   │ 执行过程                │
│ 新建会话     │ 当前阶段 / 耗时 / 停止   │ 时间线 · 计划 · Agent   │
│ 搜索会话     ├─────────────────────────┤ Trace · 上下文          │
│ 最近会话     │ 用户请求                │                         │
│ · 任务标题   │                         │ 当前正在执行的节点      │
│ · 运行状态   │ 助手进展摘要            │ 已完成与待执行步骤      │
│              │ 最终回答 / 文件产物     │ 选中节点 → 详情抽屉     │
│              │                         │                         │
│ 能力与设置   ├─────────────────────────┤                         │
│ 工具/技能等  │ 附件 · 输入框 · 发送    │ 筛选 / 跟随执行         │
└──────────────┴─────────────────────────┴─────────────────────────┘
```

- 左侧以会话为主：展示可读标题、最近更新时间和运行状态；模式移到任务头部；工具、技能、MCP、档案管理移入“能力与设置”。
- 中间保留对话、简短进展和最终产物。每个用户回合绑定一条运行记录，可点击“查看执行过程”定位对应运行。
- 右侧展示选中运行的过程；默认时间线，按模式显示计划、Agent 视图。Trace 和上下文用于深入检查。
- 文件区呈现上传与生成的文件；生成文件只有取得真实产物关联后才显示为本次任务结果，不能把整个沙箱文件列表当作本回合产物。
- 一次运行结束后显示耗时、工具调用数、失败/重试数和结果状态；点击指标可筛选相应事件。

### 3.2 视觉规范

默认采用清晰的浅色工作台，同时提供深色主题；通过 CSS 语义变量统一控制，不按页面零散设置颜色。

| 项目 | 初始设计值 / 规则 |
| --- | --- |
| 浅色基础 | 背景 `#F6F8FC`，面板 `#FFFFFF`，正文 `#172033`，次级文字 `#526079`，强调色 `#3458DB` |
| 深色基础 | 背景 `#10141D`，面板 `#181F2B`，正文 `#E8EDF5`，次级文字 `#A2AEC2`，强调色 `#8DA6FF` |
| 变量 | `--surface-*`、`--text-*`、`--border-*`、`--accent-*`、`--status-*`、`--space-*`、`--radius-*` |
| 字体 | 中文使用系统无衬线；正文 14–16px，辅助文字 12–13px，标题 18–24px；代码和标识使用等宽字体 |
| 间距与形状 | 4/8/12/16/24/32px 间距；面板内边距 16–24px；圆角 8–12px；弱阴影和明确分隔 |
| 状态 | 等待、运行、成功、失败、跳过、取消均使用图标 + 文字 + 颜色；不靠颜色单独表达含义 |
| 图标与反馈 | 统一线性 SVG 图标，替换功能区混杂 Emoji；焦点态、悬停态、选中态、禁用态一致 |
| 动效 | 仅用于状态切换和展开，约 120–180ms；支持减少动态效果偏好 |

上述颜色是起点，实施时检测实际前景/背景组合的可读性。视觉验收覆盖正常、空白、加载、失败和长文本状态。

### 3.3 响应式与阅读体验

- 宽度 ≥1280px：三栏，导航约 240px，检查区默认约 420px，主区自动分配剩余空间。
- 768–1279px：导航可折叠，检查区切为抽屉或主区标签页，避免三栏同时挤压。
- <768px：单栏主区，会话和执行详情通过独立抽屉进入；输入框保持可用。
- 用户向上阅读后暂停自动滚动，显示“有新事件 / 回到最新”；切换节点、展开详情不抢滚动位置。
- 支持键盘操作、可见焦点、抽屉焦点管理；中文输入法组合输入期间不触发 Enter 发送。
- 超长 JSON、代码、表格和文件名在自身容器内折行或滚动，不撑破页面。

## 4. 执行透明化的展示规格

| 环节 | 默认展示 | 展开后展示 | 数据改造位置 |
| --- | --- | --- | --- |
| 运行受理 | 已接收、模式、开始时间 | session/turn/execution/trace 标识 | `api/web.py`、`agent/runtime.py` |
| 上下文准备 | 正在检索记忆/准备上下文 | 使用的记忆条目、技能、消息数量、裁剪与摘要信息、估算 token | `agent/context_builder.py`、`memory/`、`skills/` |
| 计划生成 | 计划步骤及当前步骤 | 步骤输入输出、版本、工具提示、显式规划说明 | `agent/planner.py`、`agent/plan_loop.py` |
| 模型调用 | 正在生成决策/回答、已耗时 | 模型、调用序号、实际 usage、错误与重试；缺失值标记未采集 | `llm/client.py`、Runtime 中的模型包装层 |
| 工具执行 | 工具名、状态、耗时、结果摘要 | 调用 ID、完整参数、脱敏输出、错误码、各次尝试、权限结果 | `agent/react_loop.py`、`tools/gateway.py` |
| 反思与重规划 | 哪一步失败、正在调整计划 | 显式反思结论、调整原因、旧版与新版差异、替代关系 | `agent/runtime.py`、`agent/reflector.py` |
| 多 Agent 编排 | 任务归属、依赖、等待或执行状态 | 每个子 Agent 的时间线、工具、结果，以及嵌套委派 | `orchestrator/runner.py`、`executor.py`、`models.py` |
| 检查点 | 保存或恢复记录 | checkpoint ID、版本、对应节点；恢复操作另行实现 | `agent/runtime.py`、`checkpoint/` |
| 完成/失败/取消 | 明确终态与结果摘要 | 部分成果、失败位置、耗时、工具次数、可用产物 | 运行服务、事件仓库和前端运行摘要 |

具体交互规则：

1. 时间线按真实事件更新，活动节点显示运行中和已耗时；无开始事件时只显示“待执行”，不能推测已经开始。
2. 同一工具调用只对应一张逻辑卡片，重试展示在其下；多次独立调用同名工具保留多张卡片。
3. Plan 显示“完成 x/y 步”，ReAct 显示“第 n 轮”；分母因重规划变化时显示版本变化，不把未知工作量映射成伪造百分比。
4. 子 Agent 用实例 ID 区分，同一个档案名可对应多个任务。先实现分组列表和依赖关系，再增加 DAG；依赖边使用 `depends_on`，不能将调用树父子边当作依赖边。
5. Plan 步骤内的回答作为步骤结果；只有整次运行汇总成功后，才把主回答标记为最终完成。
6. 阶段一保留整段回答返回方式；若后续增加逐字输出，必须接入模型真实增量流，不能用动画伪装流式生成。
7. 取消先显示“取消请求已发送”，后端确认后再显示“已取消”。无法中断的工具须显示真实执行状态和可能已完成的操作。
8. 费用不列为首版必需指标；没有价格配置和真实 usage 时不显示金额。估算 token 与提供方返回值分别标注。

## 5. 后端与事件协议改造

### 5.1 引入独立的运行实体

新增顶层 `execution_id` 表示一次用户提交；保留已有 `turn_id` 和编排 `run_id`，通过明确字段关联，避免覆盖现有编排接口语义。

- 一条会话包含多个 execution；一次 execution 关联一个 turn、可选 trace，以及零到多个编排 run。
- `agent_instance_id` 标识实际执行实例，`agent_profile` 仅表示档案类型；`parent_agent_instance_id` 表达委派层级。
- `tool_call_id` 沿用模型调用标识并结合 execution/实例定位；内部非模型调用生成稳定 ID。
- `plan_version + plan_step_id` 定位计划步骤，`attempt` 区分重试；`span_id` 仅用于关联诊断 Span。
- 消息增加可空的 execution/turn 关联字段；旧消息继续可读，并标记“历史记录未采集完整执行过程”。

优先消除共享状态风险：将模式作为每次执行参数，运行状态和事件发布器放入独立执行上下文。可复用工具注册表、客户端和仓库，但不能复用可变 `_state`、用户上下文及回调。相同会话首版限制一次活动运行，后端返回明确冲突；不同会话的执行必须相互隔离。

### 5.2 统一事件信封

以下为拟新增协议，不是当前接口。所有事件经同一个发布器分配单调递增的 `seq` 并持久化；前端以 `event_id` 去重，用实体 ID 更新节点。

```json
{
  "schema_version": 1,
  "event_id": "evt_example_18",
  "execution_id": "exec_example",
  "session_id": "session_example",
  "turn_id": "turn_example",
  "seq": 18,
  "timestamp": "2026-09-10T07:00:00.000Z",
  "type": "tool.started",
  "agent_instance_id": "agent_example",
  "orchestration_run_id": null,
  "plan_version": 1,
  "plan_step_id": "plan_0001",
  "tool_call_id": "call_example",
  "attempt": 1,
  "trace_id": "trace_example",
  "span_id": "span_example",
  "payload": {
    "name": "get_weather",
    "arguments": {"city": "北京"},
    "status": "running"
  }
}
```

不同事件按需提供关联字段。核心事件目录：

| 类别 | 拟新增事件 |
| --- | --- |
| 运行 | `execution.accepted/started/completed/failed/cancel_requested/cancelled/interrupted` |
| 上下文 | `context.started/completed`、`memory.retrieved`、`skill.selected` |
| 计划 | `plan.created/revised`、`plan_step.started/completed/failed/skipped`、`reflection.completed` |
| 模型 | `llm.started/completed/failed/retry_scheduled`、`decision.summary` |
| 工具 | `tool.scheduled/started/completed/failed/retry_scheduled`、`tool.policy_evaluated` |
| 编排 | `orchestration.started/completed/failed`、`agent.scheduled/started/completed/failed/skipped` |
| 其他 | `checkpoint.saved/restored`、`artifact.created`；真实输出流可用时再加 `answer.delta` |

`decision.summary` 只承载实际存在的对外摘要。`context.completed` 等要注明采集范围。未启用记忆/Trace 等能力时显示“未启用”，查询失败则显示“读取失败”，不能混用。

节点基本状态为 `pending → running → succeeded/failed/skipped/cancelled`。运行另有 `cancel_requested`、`interrupted` 等状态；部分失败使用显式结果字段区分。与现有 `DONE`、`SUCCEEDED`、`PARTIAL`、Span `OK/ERROR` 的转换集中在适配层，并有映射测试。

### 5.3 持久化、续接与取消

建议沿用现有 SQLite 仓库模式，新增 `executions`、`execution_events`，大输出保存到受控详情存储。为 `(execution_id, seq)` 建唯一约束，按会话和更新时间建立运行查询索引。

拟新增 API：

| 接口 | 职责 |
| --- | --- |
| `POST /api/web/executions` | 创建运行；接收 message、session_id、mode、client_request_id，立即返回稳定标识；同一请求键避免重复执行 |
| `GET /api/web/sessions/{session_id}/executions` | 分页查询会话运行列表 |
| `GET /api/web/executions/{execution_id}` | 获取状态、累计指标和带 `last_seq` 的快照 |
| `GET /api/web/executions/{execution_id}/events?after_seq=N` | 分页读取历史事件 |
| `GET /api/web/executions/{execution_id}/stream?after_seq=N` | SSE 历史补发并转实时订阅；支持事件 `id` 和续接游标 |
| `POST /api/web/executions/{execution_id}/cancel` | 幂等请求取消，返回真实运行状态 |
| `GET /api/web/executions/{execution_id}/outputs/{output_id}` | 按需加载脱敏后的大输出或产物详情 |

关键实现约束：

- 先持久化再发布；从历史切换到实时订阅时通过序号补齐窗口，不能漏事件或重复显示。
- 快照内容与 `last_seq` 必须一致；客户端只应用后续事件。事件过期或游标不再可用时返回明确恢复指引。
- 断开订阅不等于取消执行。首版由应用生命周期管理活动任务，显式取消才终止；单进程版本重启后将遗留运行标记为 interrupted，自动续跑留待后续能力。
- SSE 增加心跳与断线退避；慢客户端使用有界缓存并通过持久化事件追赶，不能无限堆积内存或拖住 Agent。
- 新运行接口解耦任务与连接后再切换前端；旧 `/chat/stream` 在迁移期保留原语义，不在客户端不知情时改变断线行为。
- 终态至多写入一次；终态后停止改变运行结果。晚到工具结果需按明确规则记录，不能把已取消任务改成成功。
- 普通失败、取消和进程中断均保留已采集的历史。显示“记录中断”比填补虚构步骤更准确。

### 5.4 Trace 与执行事件的分工

执行事件负责用户可见的业务生命周期，Trace 负责调用层级和诊断细节；使用标识关联，避免两个来源分别创建重复节点。

- 不能只靠频繁轮询现有 JSONL 获得实时流程；业务开始/结束事件从实际生命周期发出。
- 需要实时 Trace 时，再为 Recorder 增加开始/结束订阅或运行中 Span 快照；保留现有 JSONL 格式的兼容读取。
- 工具拒绝、失败和重试应在真实网关边界发出事件；执行调度与完成事件通过同一调用 ID 关联。
- Plan 规划、步骤、反思，以及子 Agent 启动/结束须新增业务事件，不能只把现有 `after_decision` 包装成完整流程。

### 5.5 输出、内容与访问边界

- 输出保留 JSON 原始类型；空值、`0`、`false` 和空字符串明确展示，不使用真假判断决定是否存在。
- 摘要与详情分开：事件携带 preview、output_id、truncated 和可用字节数，完整详情按需读取；超过存储上限时显式说明。
- 脱敏发生在事件持久化、Trace 导出和前端传输之前；复用现有脱敏逻辑并核对新事件路径，避免实时通道绕过策略。
- Prompt/上下文继续遵守已有内容采集配置，默认展示结构和摘要；不为“透明化”默认打开完整敏感内容采集。
- Markdown 渲染统一清理 HTML 并限制危险链接协议；工具 JSON 优先用文本节点呈现。
- execution、会话、详情和产物查询采用一致的访问范围；若沿用当前单用户部署，应明确部署边界，不把传入的 session_id 当作身份认证。

## 6. 前端工程实施方式

首版建议保留 FastAPI 静态资源部署，使用原生 ES Modules 拆分现有 `app.js`，减少同时迁移框架、构建链和执行协议的工作量。组件复杂度显著上升后，再单独评估框架迁移；React/Vue 不是本计划的前置依赖。

建议目录职责如下，均为拟新增结构：

```text
app/static/
  index.html
  app.js                    # 启动与依赖组装
  styles/                   # tokens、布局、组件、主题
  api/                      # HTTP、SSE、错误与重连
  store/                    # 会话、运行、事件 reducer、选择状态
  components/               # 导航、对话、时间线、工具、计划、Agent、详情
  utils/                    # Markdown 清理、格式化、滚动策略
```

设计要求：

- 数据先进入 store，再派生视图；消息、工具、计划、Trace 不再各自在 DOM 中维护独立事实。
- 连接状态与运行状态分开管理；断网时运行状态可显示“状态待确认”，不能直接标记失败或完成。
- reducer 以 execution 和实体 ID 隔离，支持重复、补发与未知类型事件；切换会话后晚到响应不能写入当前会话。
- 详情按需加载，批量处理高频事件；长时间线超过约定阈值后采用窗口化渲染。
- 主题、面板宽度和筛选偏好可本地保存；运行事实来自后端持久化记录。
- 首版可按顺序列出子 Agent 并显示依赖；DAG、Trace 瀑布图放在基础数据准确之后实现。

## 8. 验收标准与测试计划

### 8.1 功能验收矩阵

| 场景 | 必须满足的结果 |
| --- | --- |
| 不调用工具的普通问答 | 展示运行受理、模型开始和完成、最终结果；结束前不显示成功 |
| 连续调用两次同名工具 | 两张卡片 ID、参数、输出、耗时分别准确，无覆盖 |
| 并行子 Agent 调用同名工具 | 每个结果归属正确实例；可以定位父任务和依赖 |
| 工具返回 `0/false/空字符串` | 输出可见，且不会误判成“等待执行”或缺失 |
| 工具失败、超时或重试 | 错误可展开；每次尝试可追溯；最终成功不抹除前次失败 |
| Plan 生成及执行 | 执行第一步前计划已可见；运行中持续更新步骤状态 |
| 重规划 | 保留旧版计划及失败结果；新版有原因、版本和明确替代关系 |
| 子任务失败与依赖跳过 | 实际失败、跳过和部分成果准确反映；主任务结果与子状态一致 |
| 刷新或 SSE 断线 | 使用原 execution 续接，不重新调用模型或工具；事件不丢、不重复 |
| 主动停止 | 先进入取消请求状态，再由服务端确认；已完成节点保留 |
| 服务端重启 | 遗留运行标为中断或由实际恢复机制接管，不永久假装运行中 |
| 切换会话/多浏览器运行 | 不串消息、工具状态、模式和回调；同会话重复提交按既定规则处理 |
| 未启用 Trace / 旧历史 | 基础时间线可用；分别明确展示未启用或历史数据不足 |
| 超长输出或不安全 Markdown | 详情按需加载、无页面溢出；脚本和危险链接不可执行 |

### 8.2 视觉和体验验收

- 至少在 1440×900、1024×768、390×844 三种尺寸检查；页面无非预期横向滚动，发送和停止始终可达。
- 覆盖欢迎页、普通问答、长工具输出、Plan 重规划、并行编排、断线、失败七组截图。
- 主要正文保持 14px 以上；焦点可见，状态不只依靠颜色；中文输入法不会误发消息。
- 用户在顶部摘要能直接找到当前任务、模式、真实运行阶段和耗时；从失败节点一次展开即可看到错误详情。
- 向上阅读时新事件不抢滚动；刷新后选中运行可恢复，历史与实时展示使用同一套组件。

### 8.3 指标与验证方式

以下为首轮建议门槛，使用固定开发环境和 stub/mock 事件测量，并记录硬件、浏览器、负载和采样方法：

- 不等待 LLM 返回即可显示受理状态；事件从服务端发布到可见的延迟 P95 ≤500ms（本地部署）。
- 含 1,000 条事件的历史运行首次可交互时间 ≤2 秒；10,000 条事件通过分页/窗口化保持可操作。
- 重复事件、续接补发后实体数量和最终状态与完整日志重放一致；所有具有关联 ID 的工具事件均能归属到准确卡片。
- 首版覆盖表中所有 P0 场景；C/D 完成后覆盖完整功能矩阵，未支持能力不显示为可用操作。

测试分工：

1. 后端：扩展 `tests/test_web.py`、`test_plan_loop.py`、`test_orchestrator.py`、`test_tracing.py`，新增事件仓库/协议/并发隔离测试。
2. 前端：为 reducer 和 SSE 解析增加针对重复、断帧、补发、终态和实体对应关系的单元测试。
3. 浏览器：新增端到端测试入口，使用 stub/mock 避免真实模型费用和外部副作用；验证截图、输入、会话切换、取消及恢复。
4. 集成：在隔离的本地环境执行一次真实 ReAct、Plan 和多 Agent 样例，核对时间线与服务端事实一致，不用截图替代事件正确性验证。

## 9. 迁移、交付与风险控制

- 采用增量迁移，不删除现有会话和编排记录；新增列允许为空，旧记录不伪造缺失事件。
- 通过配置保留旧 UI/协议入口直到新版验收通过；回退前端不应要求删除新增事件数据。
- 运行存储首版默认单进程 SQLite；部署为多个 API/Worker 进程前，必须解决跨进程序号分配、订阅、任务归属和取消路由。
- 事件与详细输出设独立保留策略和大小上限，明确清理后可回放到什么程度；删除会话时按既定策略处理关联运行及产物。
- 发布前更新 README 中的启动方式、执行观察说明和能力边界，欢迎页宣传与已实现能力保持一致。

最终交付应包含：新版页面、版本化事件协议、运行与事件存储迁移、前后端测试、验收截图、已知限制及回退说明。以“当前过程可见、状态可信、历史可恢复”作为透明化完成条件，以完整状态与多尺寸页面的实际验收作为界面改进完成条件。
